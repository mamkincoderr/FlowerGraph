# Код-ревью FlowerGraph: навигация и отображение

Область: `ui/plot_area.py`, `ui/nav_bar.py`, `ui/main_window.py`.
Версия pyqtgraph в проекте — 0.14.0 (сверено с исходником библиотеки).

## Сводка

Архитектура в целом аккуратная: чёткое разделение LIVE/STATIC режимов, дискретная
шкала 1-2-5, отдельный лёгкий overview-буфер. Найдена одна критическая проблема
навигации (несоответствие поведения правой кнопки мыши документации/ожиданиям),
одна проблема производительности, которая проявляется как подтормаживание
отображения, и несколько мелких недочётов.

---

## Критические проблемы

### 1. Правая кнопка мыши не панорамирует, а масштабирует — вопреки комментарию в коде

`plot_area.py`, `_install_selection_drag()`:

```python
vb.setMouseMode(pg.ViewBox.RectMode)   # правый drag = pan
...
def _drag(vb_self, ev, axis=None):
    if ev.button() == Qt.LeftButton:
        ...  # своя логика выделения
    else:
        pg.ViewBox.mouseDragEvent(vb_self, ev, axis)
```

Комментарий утверждает, что правая кнопка — это pan. Но в исходнике
`ViewBox.mouseDragEvent` (pyqtgraph 0.14.0) ветка для правой кнопки вызывает
`scaleBy(...)`, а не `translateBy(...)`:

```python
if ev.button() in [Qt.LeftButton, Qt.MiddleButton]:
    if self.state['mouseMode'] == ViewBox.RectMode and axis is None:
        self.showAxRect(ax)      # rubber-band zoom
    else:
        self.translateBy(x=x, y=y)   # pan — но левая кнопка у нас перехвачена!
elif ev.button() & Qt.RightButton:
    self.scaleBy(x=x, y=y, center=center)   # ZOOM, не pan
```

Поскольку `RectMode` включён явно, а левая кнопка полностью занята под
выделение, `translateBy` (настоящий pan) в приложении **не вызывается вообще
ни для одной кнопки**. Правый drag на самом деле «тянет» масштаб по X и Y
одновременно (как будто крутите ручку осциллографа), что для пользователя,
ожидающего обычное панорамирование зажатой правой кнопкой (как в
большинстве DAQ-программ, включая PowerGraph), выглядит как баг: график
неожиданно растягивается/сжимается вместо сдвига.

**Почему это важно**: панорамирование мышью в этом приложении сейчас
отсутствует как класс — единственные способы сдвинуть вид: колесо (дискретный
зум), стрелки на клавиатуре, кнопки NavBar, PgUp/PgDn. Это не смертельно, но
доступный факт `правая кнопка = pan` в комментарии/README вводит в
заблуждение и на практике не работает так, как задумано.

## Проблема производительности, влияющая на отображение

### 2. Полная копия кольцевого буфера каждый кадр в LIVE-режиме при `following=False`

`plot_area.py`, `_get_view_data()`:

```python
else:
    vr = self._plot.plotItem.getViewBox().viewRange()[0]
    ...
    t, v = self._buffer.get_last(self._buffer.size)   # ← копия ВСЕГО буфера
    ...
```

Когда идёт запись/мониторинг (LIVE) и пользователь снял «Следить» (например,
чтобы вручную посмотреть кусок графика во время записи), `_refresh()` вызывается
таймером с частотой FPS (по умолчанию 25, можно выставить 60) и на каждый тик
копирует **весь** кольцевой буфер (до `MAX_RING_SAMPLES = 300 000` отсчётов ×
N каналов, `float64`+`float32`), хотя реально нужен только видимый диапазон.
При большом буфере (много каналов, высокая частота) это создаёт заметные
подвисания/просадки FPS именно в момент, когда пользователь пытается
рассмотреть детали — то есть прямое ухудшение отображения в самый
неподходящий момент.

Исправление: искать нужный поддиапазон через `np.searchsorted` не по всему
буферу, а получать из `RingBuffer` только «хвост» разумного размера (как это
уже сделано в `_snap_marker` — там есть похожий паттерн с `n_vis`), либо
добавить в `RingBuffer` метод `get_range(t_lo, t_hi)`, работающий без полной
копии.

## Проблема навигации по блокам (edge case)

### 3. Границы блока (`setLimits`) могут «подрезать» окно при переходе между блоками через NavBar

`plot_area.py`, `load_block()`:

```python
t0, t1 = float(block.t_start), float(block.t_end)
self._plot.plotItem.getViewBox().setLimits(xMin=t0, xMax=t1)
```

`main_window.py`, `_on_nav_navigate()` при перетаскивании региона в NavBar
через границу блока:

```python
if target != self._current_block_idx:
    self._display_block(target, fit=False)   # → load_block(fit=False) → setLimits нового блока
...
self._plot_area.set_view_range(local_t0, local_t1)   # setXRange с текущей шириной окна
```

Если ширина текущего окна (масштаб) больше длительности нового блока, либо
запрошенный диапазон выходит за `t_start/t_end` нового блока, pyqtgraph
внутри `ViewBox.setRange` жёстко ограничивает диапазон лимитами
(`updateViewRange`/`maxRng`/`minRng`). В результате при протаскивании
region-а через «стык» между блоками (0.5 с зазор в overview) видимое окно
может резко «прилипнуть» к границе блока вместо плавного скролла — рывок
масштаба/позиции, который выглядит как глюк навигации, особенно при большом
числе коротких блоков.

Не критично (это довольно редкий edge case — сессия с несколькими блоками +
масштаб шире блока), но стоит знать.

## Что сделано хорошо

- Чёткое разграничение LIVE/STATIC режимов и единая точка входа `_get_view_data()`.
- Discrete time-division (1-2-5) с грамотным подбором ближайшего шага (`time_div_idx_for_span`).
- LOD-прореживание (`_lod_decimate`, min/max) для больших массивов перед отрисовкой.
- Отдельный лёгкий `_ov_buf` для overview в LIVE — не копирует гигантский буфер на каждый кадр обзора (в отличие от найденной проблемы №2 в основном view).
- Корректная защита от бесконечного `t_min < 0` в `_set_x_range` (сдвиг с сохранением ширины окна).
- Снепинг маркеров M1/M2 и выделения к реальным точкам данных (`_find_nearest_time`) — приятная деталь для точных измерений.

## План фиксов (по приоритету)

1. **[Критично, навигация] Починить панорамирование правой кнопкой.**
   Варианты:
   - Явно обработать `RightButton` в `_drag()`, вызывая `translateBy` самостоятельно
     (перерасчёт через `mapSceneToView` для delta вместо scaleBy), либо
   - Оставить `PanMode` вместо `RectMode` и убрать rubber-band полностью
     (раз выделение всё равно кастомное), тогда левая кнопка без перехвата
     панорамировала бы стандартно, а перехват оставить только для
     Shift+Left или отдельного режима.
   - Как минимум — исправить комментарий и один раз явно протестировать
     реальное поведение правой кнопки, задокументировав в README «зум по X/Y
     удержанием правой кнопки», если решите оставить как есть.
   Оценка: 0.5–1 день с ручным тестированием ощущений «на глаз».

2. **[Важно, производительность/отображение] Убрать полную копию буфера в `_get_view_data()`.**
   Добавить в `RingBuffer` метод `get_range(t_lo, t_hi, max_n=None)`, который
   через `get_last(N)` с оценкой `N` по частоте дискретизации (как уже сделано
   в `_snap_marker`) получает не весь буфер, а разумный хвост, и только затем
   режет `searchsorted`. Заодно unit-тест на этот метод.
   Оценка: 0.5 дня.

3. **[Желательно] Смягчить рывки на границах блоков при навигации из NavBar.**
   Перед `set_view_range` в `_on_nav_navigate` проверять, укладывается ли
   запрошенный диапазон в лимиты нового блока, и если ширина окна больше
   длительности блока — подгонять окно через `fit_to_span` вместо
   `set_view_range` с сохранением исходной ширины.
   Оценка: 0.5 дня + ручное тестирование сессии с 3–5 короткими блоками.

4. **[Мелочи, по возможности заодно]**
   - Добавить горячую клавишу пункту «Показать блок».
   - Заменить `except Exception: pass` в `_update_session_overview` на
     логирование (`logging.debug`), не меняя поведения.
   - Зафиксировать комментарием, что зум колесом центрируется на середине
     окна, а не на курсоре — осознанное решение.

Итого на критичные и важные пункты (1–2) — около 1–1.5 дня работы с ручным
тестированием на реальном источнике данных (COM/генератор).
